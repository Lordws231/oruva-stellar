Oruva Intents Tester Docs

Use and test Oruva Intents on Stellar testnet. Back to the developer dashboard.

Sandbox and testnet only No real funds move here. Amounts are capped at 10 test units per intent, settlement is simulated, and fiat payout is not available. Production use stays gated on custody validation, SEC/VASP legal clearance, partner approvals, an independent penetration test and founder mainnet authorization.

Quickstart

Issue a sandbox key, then run quote, submit and simulate-fill:

curl -X POST "$BASE/tester/v1/keys" -H 'content-type: application/json' \
  -d '{"label":"my-app"}'

curl -X POST "$BASE/tester/v1/intents/quote" \
  -H 'content-type: application/json' -H "x-api-key: $TESTER_KEY" \
  -d '{"kind":"swap_convert","inputAsset":"USDC","inputAmount":5,"outputAsset":"USDC","outputChain":"stellar","minOutputAmount":4,"recipient":"G...","deadline":"2026-12-01T00:00:00.000Z"}'

curl -X POST "$BASE/tester/v1/intents/submit" \
  -H 'content-type: application/json' -H "x-api-key: $TESTER_KEY" \
  -d '{"quoteId":"<quoteId>","idempotencyKey":"run-1"}'

curl -X POST "$BASE/tester/v1/intents/<intentId>/simulate-fill" \
  -H "x-api-key: $TESTER_KEY"

In the dashboard, set the API base to your tester host plus /tester and paste the sandbox key.

Endpoints

RoutePurpose
GET /tester/v1/healthNetwork, mode, caps and routes. No key required.
POST /tester/v1/keysIssue a sandbox key. The raw key is shown once.
POST /tester/v1/intents/quoteRequest a capped sandbox quote.
POST /tester/v1/intents/submitOpen an intent. Idempotent per key.
GET /tester/v1/intents/:intentIdIntent status, balances and events.
POST /tester/v1/intents/:intentId/simulate-fillSimulate fill and settlement on Stellar routes.
POST /tester/v1/intents/:intentId/refundRefund after the deadline passes.
POST /tester/v1/resetClear your own sandbox records.

Rules of the sandbox

  • Send x-api-key: oruva_test_... on every call except health and key issuance. Live keys are rejected.
  • Records are isolated per key. Another key cannot see your quotes or intents.
  • Lifecycle: open, then filled and settled through simulate-fill, or refunded after the deadline.
  • Cross-chain tester intents stop at filled until delivery proof verification.
  • Rate limits: 60 requests per minute per key, 5 key issuances per hour per label.
